# Deployment

NOTE: This file was generated by AI (GitHub Copilot) on 2025-11-14.

Guidelines for deploying TPNEBOT to production like environments.

## Baseline Assumptions
- Target platform: Linux host or container (Windows acceptable for development).
- Postgres accessible locally or over secure network channel.
- Python 3.11+ installed.

## Steps (Bare Metal)
1. Create dedicated system user:
   useradd -r -s /bin/false tpnebot
2. Install Python and Postgres packages via system package manager.
3. Clone repository into a directory owned by tpnebot user.
4. Create virtual environment and install requirements:
   python -m venv /opt/tpnebot/venv
   source /opt/tpnebot/venv/bin/activate
   pip install -r requirements.txt
5. Create `.env` with production credentials (restrict file permissions).
6. Test run:
   python bot.py
7. Configure systemd unit (example skeleton):
```
[Unit]
Description=TPNEBOT Discord Bot
After=network.target

[Service]
Type=simple
User=tpnebot
WorkingDirectory=/opt/tpnebot
EnvironmentFile=/opt/tpnebot/.env
ExecStart=/opt/tpnebot/venv/bin/python bot.py
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```
8. Enable service:
   systemctl enable tpnebot
   systemctl start tpnebot

## Docker (Suggested)
### Dockerfile (Example Sketch)
```
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "bot.py"]
```
Build and run:
```
Docker build -t tpnebot:latest .
Docker run --env-file .env --name tpnebot --restart unless-stopped tpnebot:latest
```
Note: Ensure Postgres hostname inside URL references service name or external host.

## Environment Separation
- Use distinct tokens and seeds per environment (dev, staging, production).
- Avoid running development fairness seed rotation in production without auditing.

## Observability
- Tail `discord.log` for operational events.
- Consider exporting metrics: integrate a small HTTP server or push counters to external monitoring.

## Backups
- Database dumps (pg_dump) on regular schedule.
- Preserve blockchain blocks and transaction history for audit.

## Scaling
- For large guild counts: consider sharding (discord.py has sharding support).
- Use connection pool tuning for asyncpg (configure in manager code).

## Zero Downtime (Optional)
- Use rolling container updates or systemd service restart with health checks.
- Persist seeds and wallet state before upgrade.

## Security Hardening
- Restrict outbound network if not needed.
- Keep dependencies pinned but update when security patches release.
- Monitor resource usage (memory, CPU) and set ulimits where appropriate.
