# Contributing

NOTE: This file was generated by AI (GitHub Copilot) on 2025-11-14.

Thank you for your interest in contributing to TPNEBOT. This guide explains how to propose changes effectively.

## Ground Rules
- Maintain code readability and follow existing naming and structural patterns.
- Avoid introducing heavy dependencies without discussion via an issue.
- Performance matters: prefer async, avoid blocking calls inside command handlers.
- Security first: never log secrets, tokens, seeds, or private keys.

## Getting Started
1. Fork the repository.
2. Create a feature branch:
   git checkout -b feature/short-description
3. Install dependencies in a virtual environment (see README).
4. Create a `.env` file with test token and database credentials.
5. Run the bot locally and exercise new functionality.

## Issues
- Use clear titles and include reproduction steps if reporting a bug.
- Tag issues: bug, enhancement, documentation, security.
- For game fairness modifications include probability math and verifier updates.

## Pull Requests
- Keep scope focused; unrelated changes should be separate PRs.
- Describe rationale, implementation summary, and testing steps.
- Reference related issues using: Fixes #<issue-number>.
- Ensure all added modules have docstrings or minimal top level description if complex.

## Code Style
- Follow PEP8 except where existing code intentionally deviates.
- Avoid one letter variable names except for short loop indices.
- Use explicit imports and avoid wildcard imports.
- Keep functions small; refactor large command handlers into helpers when complexity grows.

## Testing
- Manual testing: verify commands respond correctly, cooldowns apply, permission restrictions function.
- Fairness: reproduce a sample outcome with the verifier to confirm deterministic behavior.
- Database: confirm new tables initialize and queries operate under concurrency.

## Adding a Cog
1. Create `cogs/<name>.py`.
2. Implement a `setup(bot)` function to add the cog.
3. Guard admin or owner only commands with proper checks.
4. Document user facing commands in the cog file header.
5. Update `BotConfig` loaded_cogs list if selective loading is enforced.

## Adding a Fairness Game
1. Implement command logic using existing HMAC helpers or similar pattern.
2. Assign deterministic nonce consumption order.
3. Add a verifier function to `utils/fairness.py` matching the production draw sequence.
4. Document math and expected return fields.

## Database Changes
- Add new SQLAlchemy model in `database/models.py`.
- Provide initialization logic if required (manager file) without dropping existing data.
- Consider forward compatible fields (nullable plus default) to avoid breakage for existing rows.

## Documentation
- Update relevant markdown files (README, ARCHITECTURE, DATABASE) along with code changes.

## Release Process (Suggested)
1. Merge approved PRs.
2. Update version string in `bot.py`.
3. Tag release: git tag -a vX.Y.Z -m "Release vX.Y.Z"
4. Push tag: git push origin vX.Y.Z

- Follow the Code of Conduct.
