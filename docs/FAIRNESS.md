# Provable Fairness

NOTE: This file was generated by AI (GitHub Copilot) on 2025-11-14.

This document describes the provable fairness implementation for TPNEBOT games found in `utils/fairness.py`.

## Goal
Provide deterministic, verifiable game outcomes to users and auditors using cryptographic HMAC based random draws that can be reproduced off chain with disclosed seeds.

## Core Concepts
- Server Seed: Secret value stored per wallet. Must be unpredictable.
- Client Seed: User set or default seed allowing user participation in entropy.
- Nonce: Incrementing counter per draw ensuring each HMAC message remains unique.
- Tag: Context string for namespacing different draw types (randbelow, random, shuffle i, choice, etc.).

## Random Generation Method
Each draw computes:
HMAC_SHA256(key=server_seed, message=client_seed:nonce:tag)
First 8 bytes of digest produce a 64 bit unsigned integer (u64). Rejection sampling removes bias for modulo operations using a limit threshold (uniform mapping to [0, n)).

## Unbiased Mapping
- Compute limit = 2^64 - (2^64 mod n).
- If u64 >= limit rehash u64 via SHA256 of its 8 byte form and retry.
- Return u64 mod n for final unbiased result.

## Game Verification Functions
The verifier class `ProvenFairness` mirrors production logic. Key examples:
- `verify_gamble`: Single binary draw (win or loss) via randbelow(2).
- `verify_supergamble`: Two consecutive percentile draws for win and bonus evaluation.
- `verify_dice`: Two six sided rolls using consecutive nonces.
- `verify_ladder`: Percentile draw compared against step threshold probabilities.
- `verify_slots`: Six weighted symbol selections using cumulative buckets.
- `verify_blackjack`: Fisher Yates style shuffle with per swap tagged draws then first cards distribution.
- `verify_roulette`: Choice among 0 to 36 plus 00 returning color and parity flags.
- `verify_poker`: Shuffle then deal player, bot, and community cards.
- `verify_mines`: Partial Fisher Yates sampling of bomb positions.
- `verify_crash`: One uniform draw mapped through a multiplier function.

## Shuffle Integrity
Deck shuffle uses a reverse loop Fisher Yates algorithm. Each swap uses a tag shuffle:i so independent draws produce deterministic positions. Verifier reproduces identical sequence given seeds and starting nonce.

## Reproducing Outcomes (Example)
Given: `server_seed`, `client_seed`, starting nonce, and internal game parameters.
1. Identify draw sequence and number of draws from game logic.
2. Apply verifier function with same inputs.
3. Compare results to recorded GameHistory entry (hash, wagered, outcome fields) if stored.

## Security Considerations
- Server seed secrecy is critical pre game. Revealing only after rotation allows verification without enabling prediction.
- Rotation should archive previous server seed and reveal it only after all games using that seed finalize.
- Client seed changes must not reset nonce unexpectedly; resetting can enable partial prediction windows.

## Auditing Steps
1. Fetch `GameHistory` row (contains `user_id`, `game_name`, `client_seed`, `used_server_seed`, `nonce`, `hash`).
2. Run corresponding verifier with stored seeds and nonce.
3. Confirm deterministic outputs match logged outcome and compute hash of game record fields. Compare with stored hash.

## Extending Fairness
When adding a new game:
1. Define nonce consumption pattern clearly.
2. Implement production logic using existing HMAC helpers or same pattern.
3. Add a verifier function replicating draws exactly in order.
4. Document expected outputs and any probability distribution details.

## Common Pitfalls
- Using modulo without rejection sampling introduces bias for non power of two ranges.
- Reusing nonce for multiple distinct draws with same tag risks correlated outputs.
- Logging seeds prematurely compromises fairness integrity.
